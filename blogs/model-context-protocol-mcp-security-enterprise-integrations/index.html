MCP security for enterprise integrations: identity, tools and trust boundaries

The Model Context Protocol can connect AI applications to tools and business systems. That connection creates real security boundaries: who is calling, which resource is being accessed, what a tool may change and how an action can be audited.

Understand the MCP trust boundary

Model Context Protocol (MCP) standardises how clients and servers expose context and tools to applications. In an enterprise integration, an MCP server may sit between an AI client and a business API, document store, database or internal service. The protocol can make capabilities easier to connect, but it does not make every connected tool safe by default.

Separate the identity of the human user, the AI client, the MCP server and the downstream service. Each component has a different role and should receive only the permissions it needs. A tool that can read a document should not automatically be allowed to edit, export or delete it.

Authentication is not the same as authorization

Authentication establishes which client or user is making a request. Authorization determines which operation that identity may perform on a particular resource. Validate both at the server boundary and again where sensitive downstream operations occur. Do not assume that a tool call is safe merely because it came through an authenticated client.

Use the current MCP authorization specification and OAuth security guidance for implementations that require authorization. The specification highlights resource indicators and token audience binding so a server can validate that a token was issued for the intended resource. Read the MCP authorization security considerations.

Validate token audience and prevent token passthrough

A token issued for one service should not become a general-purpose credential for another. Validate issuer, audience, expiry, scopes and the intended resource. Do not accept a token simply because it is syntactically valid, and do not forward a client token to an unrelated downstream API.

Use a deliberate authorization flow for each downstream system. Where a service needs its own credential, obtain and protect that credential through the approved authorization mechanism. Keep access tokens out of model-visible text, tool output, debug logs and error messages.

Design tools with least privilege

Expose narrow business actions rather than a universal tool that accepts arbitrary URLs, SQL, shell commands or file paths. Validate input schemas, allowed identifiers, data types, size limits and business rules. Use allowlists for resource targets and reject unexpected fields instead of silently ignoring them.

Prefer read-only operations for discovery and analysis. Require explicit confirmation for sending messages, changing records, issuing refunds, provisioning resources or deleting data. Make high-impact operations idempotent where possible, and return a clear action summary so the caller and user can see what happened.

Treat retrieved content as untrusted input

Documents, web pages, tickets and repository files can contain instructions that attempt to influence an AI system. Treat retrieved content as data, not as a new authorization policy. Tool permissions should be enforced by the server and must not be widened because a document or model response requests it.

Keep user instructions, trusted system policy and untrusted tool content clearly separated. Validate output before passing it to another tool. Apply data-loss controls and privacy rules to prevent sensitive records from being copied into unrelated systems or exposed to a user who lacks access.

Make actions observable and reversible

Record the authenticated principal, client identity, tool name, target resource, decision, time, result and correlation identifier. Avoid logging full secrets or unnecessary personal data. Ensure logs can support an investigation without becoming a second source of sensitive information.

Set rate limits and timeouts. Bound retries and make them safe for non-idempotent operations. Provide a way to revoke credentials, disable a tool and investigate unusual access. For actions that cannot be reversed, use preview-and-confirm patterns and retain an auditable approval record.

A practical MCP security review

  • Map the user, client, MCP server and downstream service identities.
  • Validate authorization and token audience at every relevant boundary.
  • Expose narrowly scoped tools with strict input validation.
  • Keep secrets and privileged operations outside model-controlled content.
  • Require human approval for high-impact actions.
  • Test prompt injection, confused-deputy paths, replay and unauthorized resource access.
  • Log decisions and provide credential revocation and incident procedures.

Plan integrations around the business risk

An MCP integration should be reviewed like any other software integration that can reach business data or perform actions. Start with the user journey, data classification, downstream permissions and failure modes. Then choose the smallest useful set of tools and prove that policy is enforced even when the model or retrieved content behaves unexpectedly.
