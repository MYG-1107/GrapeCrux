PostgreSQL 19: New Features, Performance Changes and Upgrade Guide

PostgreSQL 19 was released on 19 November 2026. The release brings changes for database maintenance, query planning and logical replication. Here is what application and database teams should review before moving a production system.

The headline changes in PostgreSQL 19

The PostgreSQL Global Development Group released version 19 on 19 November 2026. One notable addition is `REPACK (CONCURRENTLY)`, which reorganizes table contents while allowing reads and writes to continue. The release also introduces the `pg_plan_advice` and `pg_stash_advice` extensions for controlling and applying query-planner advice.

The official release notes describe performance improvements in areas such as I/O worker scaling and foreign-key checks. Logical replication can now be enabled without a server restart when `wal_level` is set to `replica`, and sequence values can be replicated. Review the full notes for details that affect your particular workload.

Where the changes may help

`REPACK (CONCURRENTLY)` is relevant for tables that accumulate bloat or need physical reorganization without a maintenance window that blocks normal access. It does not remove the need to test disk headroom, locking behaviour and the effect on replicas. Run it first against a staging copy with representative table size and traffic.

Planner advice is useful for teams investigating unstable plans or workloads where a query's performance changes after data distribution shifts. Treat planner hints as a targeted tool, not a replacement for correct statistics, indexes or query design. Record the query, plan and reason for any advice so another engineer can maintain it.

Plan a major-version upgrade properly

A major PostgreSQL upgrade is not the same as a minor patch. Review extension compatibility, collation changes, authentication settings, replication slots, backup tooling, drivers and connection poolers. Test the upgrade path with a recent production-like copy and verify both read and write workloads.

Choose a migration approach such as `pg_upgrade` or dump-and-restore based on database size, downtime tolerance and operational constraints. Test rollback before the production window. A backup is useful only if the team has demonstrated that it can be restored.

Applications and replication need their own tests

Run application integration tests against PostgreSQL 19 rather than relying only on database-level checks. Include prepared statements, transaction boundaries, time zones, JSON and array handling, extension behaviour and connection pool recovery. If you use logical replication, test sequence state and subscriber behaviour after failover or reconnect.

Compare query plans, latency, write throughput, vacuum behaviour and replication lag before and after the upgrade. Keep a list of queries that regress so the team can investigate them with repeatable evidence.

A measured rollout

Upgrade a development environment, then a staging database, before selecting a low-risk production workload. Keep extension versions pinned and maintain a tested rollback plan. The PostgreSQL release notes should be the source of truth for feature and migration details; do not copy settings from an older upgrade guide without checking their current meaning.
