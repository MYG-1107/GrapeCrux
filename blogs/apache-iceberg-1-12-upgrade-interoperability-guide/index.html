Apache Iceberg 1.12: upgrade planning and interoperability checks

Open table formats keep evolving, and upgrades can affect more than the table library itself. Apache Iceberg 1.12.0 includes notable data-type improvements and compatibility changes. This guide turns the release into a practical platform upgrade checklist.

Why the 1.12.0 release matters

Apache Iceberg 1.12.0 was announced on October 5, 2026. The project highlights improvements for Variant data and geospatial types, together with changes across supported engines and APIs. The release notes also identify compatibility and removal changes that teams should review before upgrading.

A table format sits between storage, catalogs and compute engines. An upgrade therefore needs to consider writers, readers, catalog services, connectors, schema evolution, maintenance jobs and downstream consumers—not just one dependency version.

Review Variant and geospatial workloads

The release announcement describes faster reads for unshredded Variant values through a vectorized Parquet path in supported Spark versions and broader Variant writing support beyond Spark. It also adds read and write support for geospatial types. These improvements may matter for semi-structured event data and location-oriented analytics.

Before enabling a new type in production, confirm that every engine can read, write, filter and preserve it correctly. Test nulls, mixed types, schema evolution, statistics, partition pruning and cross-engine round trips.

Check compatibility and removed APIs

Iceberg 1.12.0 removes support for some older integrations and deprecated APIs. Its release notes identify Spark 3.4 and Flink 2.0 among removed support lines and list removals across Spark, Flink, core and AWS-related components. Review the full upstream notes for your exact connector stack.

Create a matrix of Iceberg, Spark or Flink, catalog, object-store client, Kafka Connect, serialization formats and custom extensions. Compile and run integration tests against the target combination before changing shared production libraries.

Upgrade with staging, observability and rollback

Test reads, writes, deletes, compaction, snapshots, expiration, schema changes, partition evolution and catalog operations using representative tables. Exercise recovery and rollback. Compare query performance, planning time, commit latency, metadata growth, object-store requests and job failures before and after the upgrade.

  • Read the complete 1.12.0 release notes and breaking changes.
  • Inventory engines, connectors, catalogs and custom APIs.
  • Test Variant, geospatial and schema evolution where used.
  • Verify IAM, storage clients, retries and catalog operations.
  • Roll out gradually with performance baselines and rollback criteria.

Example: validate a mixed-engine table before rollout

A data platform may have Spark jobs writing curated tables, Flink jobs reading recent events, and SQL engines serving analysts. An Iceberg library upgrade can appear successful in one engine while another fails to interpret metadata or a newer data type. Build a compatibility matrix for the exact production versions, then run the same table through every supported writer and reader. Include snapshots, deletes, partition evolution, schema changes and maintenance operations.

For Variant and geospatial workloads, create representative values and test round trips across engines before making the types part of a published data contract. A consumer that silently drops an unsupported value is more dangerous than one that fails clearly.

Release gates for table-format upgrades

  • Pin a supported matrix of engine, connector, catalog and client versions.
  • Run integration tests against production-like metadata and object storage.
  • Compare query plans, commit latency, metadata size and storage requests.
  • Test restore and rollback, including recovery from interrupted jobs.
  • Publish migration notes for downstream teams and data-product owners.

Use the upstream release notes as the authoritative change record and revisit the matrix whenever another engine or connector is upgraded.
