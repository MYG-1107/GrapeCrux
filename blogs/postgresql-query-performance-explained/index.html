PostgreSQL query performance: indexes, EXPLAIN and practical tuning

A slow database query is rarely fixed well by guessing. It needs evidence: the query shape, the data distribution, the execution plan and the user journey affected. PostgreSQL provides strong tools for understanding how a query is planned and executed. A disciplined tuning process can improve response times without adding unnecessary indexes or complexity.

Start with a user-visible symptom

Begin with the request or screen that feels slow. Identify the endpoint, report, background job or transaction involved, then record representative latency and the number of rows or records involved. A query that takes 20 milliseconds in a development database may behave very differently with production data, concurrent activity and realistic network conditions. Capture the exact SQL statement and representative parameters before changing it.

Separate database execution time from application time. A slow page may be waiting on several sequential queries, serialising a large response or opening too many connections. Use request tracing and database metrics together. A database-only benchmark can miss the application behaviour that users actually experience.

Read the plan before changing the query

PostgreSQL's EXPLAIN command shows the plan selected by the query planner. The plan describes scans, joins, estimated row counts and the expected cost of operations. EXPLAIN ANALYZE also executes the statement and reports observed timing and row counts. Compare estimates with actual values: a large mismatch can indicate stale or insufficient statistics, skewed data or a query shape that is difficult to estimate.

Read plans from the leaves toward the top. Look for sequential scans over very large relations, unexpectedly high row counts, expensive sorts, repeated nested-loop work or large differences between estimated and actual rows. A sequential scan is not automatically a defect; it may be the cheapest choice when a query needs a large share of a table. The question is whether the plan matches the workload and data volume.

Choose indexes for real access patterns

Indexes help PostgreSQL locate rows without reading every page of a table, but each index consumes storage and adds work to inserts, updates and deletes. Design them around frequent filters, join keys and sort patterns. A composite index can be useful when a query repeatedly filters on several columns, but column order matters. Test the actual query and consider whether a partial or covering index is appropriate.

Do not create an index for every column that appears in a query. Inspect existing indexes first, look for duplicates and check whether they are used by meaningful workloads. Keep write-heavy tables in mind: additional indexes can slow ingestion and increase maintenance overhead. Index design is a workload decision, not a checklist exercise.

Keep statistics and table health in view

The planner depends on statistics to estimate selectivity and row counts. Autovacuum and auto-analyze are important parts of normal operations. After significant data changes, verify that statistics are current before drawing conclusions from a plan. Tables with heavily skewed values or correlated columns may need extended statistics or a better data model.

Vacuuming, bloat, dead tuples and long-running transactions also affect database health. Treat maintenance as an operational process. Monitor autovacuum activity, replication lag where relevant, disk utilisation and transaction age. Avoid applying maintenance commands blindly during peak traffic; understand their locking and resource effects first.

Make pagination and data access predictable

Large offset-based pagination can become increasingly expensive because the database may need to walk past many rows before returning the next page. For large datasets, consider keyset pagination using a stable indexed ordering key. Make the ordering deterministic, especially when several rows share the same timestamp. Define a cursor format that cannot be altered to bypass access checks.

Return only the columns a screen needs. Avoid loading large text or binary fields into list views when they are not displayed. Review N+1 query patterns in application code, and batch work where it improves clarity without creating unbounded queries. Use prepared statements and parameter binding rather than constructing SQL from user input.

Control connections and concurrency

Every application process opening too many database connections can exhaust server resources. Use connection pooling where appropriate, configure pool limits based on the deployment architecture and set sensible timeouts. Measure active, idle and waiting connections under representative load. A queue of requests waiting for a connection can look like slow SQL even when the statement itself is fast.

Transactions should be as short as the business operation allows. Avoid holding database locks while waiting for a user, a remote API or a long-running computation. Identify lock contention and deadlocks through logs and monitoring. Retry only the transactions that can be safely retried, and make retry behaviour bounded and observable.

Build a repeatable tuning loop

Record a baseline, change one thing at a time and run the same representative workload again. Keep the query, plan, data scale, database version and measurement conditions with the result. Validate correctness as well as speed: a rewritten query must preserve filtering, ordering, null handling, permissions and business rules. Add regression tests for critical queries and review performance after schema or workload changes.
