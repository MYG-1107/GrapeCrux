A practical quality plan for web products: from manual QA to automation

Quality is not a final inspection performed just before launch. It is a set of decisions and feedback loops that help a product behave as expected for real users. A useful testing plan combines risk analysis, manual exploration, automation, API checks and clear release criteria.

Start with the risks that matter

List the journeys that create value or protect the business: account creation, sign-in, checkout, approvals, data entry, reporting, file upload or customer support. For each journey, consider the impact of failure, number of users affected, sensitivity of the data and complexity of connected systems. Prioritise tests around those risks rather than trying to give every screen the same amount of attention.

Turn requirements into observable acceptance criteria. “The form should work” is too vague. A better criterion states what valid input looks like, what happens when a field is missing, how errors are announced and what successful submission changes. Include permissions, edge cases and expected behaviour when a dependent service is unavailable.

Manual testing finds problems that scripts may miss

Manual functional testing is effective for new features, changing requirements and unusual combinations. Exploratory testing lets a tester investigate the product with a clear charter, such as “try to submit an order with conflicting delivery details.” Record the browser, device, build, data and steps. A defect report should let another person reproduce the issue without a meeting.

Test both expected and unexpected usage. Try long text, empty states, duplicate actions, slow connections, expired sessions and back-button navigation. Review labels and messages from the user’s perspective. A workflow can be technically successful but still confusing, inaccessible or difficult to recover when something goes wrong.

Automate stable, high-value journeys

Automation is most useful for repeatable checks that protect important behaviour. Browser automation can cover a critical route through sign-in, navigation and a transaction. API tests can validate contracts and business rules at a lower level. Unit tests protect individual functions. The layers should complement one another rather than duplicate every assertion at every level.

Choose selectors that reflect accessible names or stable test identifiers. Use isolated test data and clean setup. Avoid fixed sleeps; wait for meaningful application state. Keep assertions close to the action they verify and ensure failures provide a useful trace. A flaky test that fails randomly teaches the team to ignore the suite, so investigate instability rather than simply rerunning until green.

Test APIs and integrations directly

APIs deserve explicit tests for authentication, authorisation, validation, response formats, pagination, rate limits and error handling. Verify that one user cannot read or change another user’s records. Test malformed inputs, missing fields, stale tokens and forbidden actions. Check that errors do not disclose secrets or internal stack traces.

For integrations, test network timeouts, retry behaviour, duplicate events, delayed callbacks and partial failures. A payment or order operation should not happen twice because a client repeated a request. Use idempotency keys or another clear deduplication design where appropriate. Validate the complete business outcome across both systems, not only an HTTP status code.

Include performance and accessibility

Performance checks should represent expected traffic and high-value operations. Measure response time, throughput, resource use and degradation under load. Check both average behaviour and slower percentiles; a good average can hide a poor experience for a meaningful group of users. Establish budgets for the endpoints and page journeys that matter.

Accessibility should be part of ordinary quality work. Test keyboard navigation, focus visibility, semantic headings, form labels, error announcements, contrast and zoom behaviour. Automated tools are useful for detecting some issues, but manual keyboard and assistive-technology checks remain important. Responsive testing should cover the actual range of devices and browser combinations used by the audience.

Make regression testing selective and sustainable

A growing product can accumulate a large regression suite. Organise tests by user journey, risk and ownership. Run fast checks on every change, broader integration tests at appropriate stages and longer performance or end-to-end suites on a planned cadence. Retire obsolete tests when the product changes. Maintain test data and document environment dependencies so that failures remain meaningful.

Use release gates, not a vague green tick

Before release, review critical journey results, unresolved high-severity defects, migration checks, permissions, backup readiness, monitoring, rollback options and acceptance by the responsible owner. If a risk is accepted, record who accepted it and why. After release, monitor production errors and user feedback. Feed incidents and support requests into the next test plan.
