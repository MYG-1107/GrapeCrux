Apache Polaris 1.9.0: What Iceberg Platform Teams Need to Check

Apache Polaris 1.9.0 arrived on 14 November 2026 with changes that affect authentication, catalog APIs and client compatibility. If your data platform uses the Iceberg REST catalog, check these details before upgrading.

Why the 1.9.0 release deserves a compatibility check

Apache Polaris is an open catalog for Apache Iceberg that exposes the Iceberg REST API to engines such as Spark, Flink and Trino. Version 1.9.0 was released on 14 November 2026. Its release notes include changes to principal handling, storage credentials, catalog configuration and list pagination.

This is not just a version bump for the catalog service. Clients, identity providers, policy engines, migration scripts and operational dashboards may depend on the behaviours that changed. Read the release notes alongside the versions of Spark, Iceberg and connectors actually used in your platform.

Pay attention to pagination defaults

Polaris 1.9.0 enables `LIST_PAGINATION_ENABLED` by default. Clients that request a page size or provide a page token must follow the returned next-page token to collect all results. A tool that previously assumed one list response contained every namespace, table or view may now show incomplete results if it does not handle pagination correctly.

Test your catalog clients with more objects than fit in one page. Confirm that the client handles empty pages, invalid tokens, retries and the final page. Update scripts and administrative tools before relying on them for inventory or access reviews.

Review authentication and storage settings

The release adds support for external principals when configured with an external identity provider and policy decision point. It also introduces an optional S3 `credentialVendingMechanism` field, with STS as the supported mechanism in this release. Check how the catalog's identity model maps to your organization and whether the new configuration aligns with your existing IAM rules.

Polaris 1.9.0 also upgrades Apache Iceberg to 1.12.0. The release notes mention a required schema v6 migration for the relational JDBC metastore before starting this version. Treat that migration as a planned change with a backup and recovery procedure, not as an incidental startup step.

Improve commit recovery and access checks

The release notes describe a change to table and view commits when the metastore outcome is unknown. Newly written metadata is no longer deleted in that situation, helping avoid cleanup that could damage a commit that may have succeeded. This is important for intermittent network failures, where a client may lose its connection before learning whether a commit completed.

Review how your applications retry commits and reconcile uncertain outcomes. Also check the new `CATALOG_READ_CONFIG` privilege and the setting that controls authorization for the catalog configuration endpoint.

Upgrade test plan

Use a staging catalog with representative numbers of namespaces, tables, views, principals and storage locations. Test pagination, external identity, credential vending, catalog configuration access, commit retries and schema migration. Check Spark, Flink and other client versions in a compatibility matrix.

Roll out one environment at a time and keep logs for authentication failures, list requests and commit outcomes. The official 1.9.0 release notes contain the definitive list of breaking changes and upgrade notes.
