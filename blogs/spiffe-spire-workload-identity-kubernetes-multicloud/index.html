SPIFFE and SPIRE: Short-Lived Workload Identity for Kubernetes

Applications need identities just as people do. SPIFFE and SPIRE provide a way to identify workloads and issue short-lived credentials, helping teams reduce the number of static secrets stored in CI systems and containers.

Give services an identity that travels with the workload

A Kubernetes service may call a database, message broker or external API. Teams often store an API key or client secret in a Kubernetes Secret and rotate it on a schedule. That can work, but it creates a long-lived credential that must be distributed, protected and revoked.

SPIFFE defines a standard way to identify software workloads. A workload receives a SPIFFE ID and can obtain a short-lived SVID (SPIFFE Verifiable Identity Document) to prove that identity to another service. SPIRE is a common implementation that attests workloads and issues those credentials.

Understand the trust chain

A SPIFFE ID identifies the workload within a trust domain. The SPIFFE Workload API allows an authorized process to request identity material. An X.509-SVID is a certificate-based identity; a JWT-SVID is a signed token that can be validated by a service that trusts its issuer and audience.

The difference matters when integrating with an external provider. Microsoft Entra's documented SPIFFE/SPIRE tutorial shows a Kubernetes workload receiving a JWT-SVID from SPIRE and exchanging it for an Entra access token. The workload does not need to keep a permanent client secret for that flow.

Use federation instead of copying secrets

Where a cloud or API provider supports workload identity federation, configure it to trust a specific issuer, audience and workload identity. Restrict which namespaces, service accounts or deployment pipelines can obtain the identity. Give different environments separate identities and permissions.

OpenAI's workload identity federation documentation describes accepting SPIFFE JWT-SVIDs as subject tokens for short-lived API access, with explicit requirements for issuer, audience, expiration and signing-key verification. Check the provider's exact requirements; a valid SPIFFE token is not automatically accepted by every service.

Operate the identity system carefully

SPIRE becomes part of the trust infrastructure. Protect server and agent configuration, restrict who can register workloads and audit changes to selectors and registration entries. Monitor certificate and token issuance, expiration, rotation and failed attestation. Keep time synchronization and trust-bundle distribution reliable.

Do not create one broad identity for every pod. Use workload-specific identities and short-lived permissions that match the service's role. A compromised workload should not inherit the access of unrelated services.

A realistic adoption path

Pilot SPIFFE on one service-to-service connection that currently relies on a static secret. Measure the operational work required to deploy the agent, issue identity, rotate credentials and recover from an issuer outage. Add more workloads after the team has a clear process for trust-domain ownership and incident response.

Short-lived identity reduces secret sprawl, but only if the workload identity system is itself governed and monitored.
