Non-human identity management: securing service accounts and workload tokens

Applications, pipelines, containers, agents and integrations use identities of their own. These non-human identities often outnumber human users and can retain broad permissions long after the original project has ended.

Treat every machine identity as an account

A non-human identity can represent a service, build job, container, integration, scheduled task, data pipeline or automated agent. It can read data, deploy code, call APIs and change infrastructure. If its permissions are broad or a credential is leaked, an attacker may gain access without logging in as a person.

Inventory identity, owner, purpose, environment, resources accessed, authentication method, expiry and last use. Unknown or ownerless identities are risks to resolve, not harmless leftovers.

Prefer short-lived identity over permanent secrets

Where supported, use workload identity federation or an equivalent mechanism to exchange a trusted workload assertion for short-lived credentials. This reduces the need to store long-lived keys in source code, CI variables or container images.

Where static secrets remain necessary, store them in a managed secret system, restrict retrieval, rotate them and monitor use. Never place credentials in logs, prompts, issue comments or build artifacts.

Apply least privilege and lifecycle governance

Give each workload a separate identity where practical. Scope access to required resources and actions, and separate development, test and production. Validate issuer, audience and subject restrictions in federation policies so a trusted token cannot be reused in an unrelated context.

Create, approve, rotate, review and retire identities through a defined lifecycle. Tie ownership to a team or service registry. Reassess permissions when purpose changes, and remove identities when a project ends.

Monitor behaviour and test revocation

Log authentication, token issuance, permission changes and high-impact actions. Alert on unusual service paths, privilege escalation and credentials used by inactive workloads. Keep logs protected from the same identity being monitored, and assign an owner who can respond.

  • Discover service accounts, tokens, API keys and workload identities.
  • Assign purpose, owner, environment and review date.
  • Prefer federation and short-lived credentials.
  • Enforce narrow permissions and separate environments.
  • Monitor issuance, usage and privilege changes.
  • Test revocation and retire unused identities.
