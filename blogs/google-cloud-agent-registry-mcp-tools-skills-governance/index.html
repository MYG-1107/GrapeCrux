Google Cloud Agent Registry: Managing MCP Servers, Tools and Skills

As businesses connect more AI agents to internal systems, they need a clear record of which tools exist, who owns them and what an agent is allowed to do. Google Cloud's recent Agent Registry updates are a useful example of that shift.

Why an agent registry matters

An enterprise agent may call an MCP server, use a tool maintained by another team or load a reusable skill package. Without a shared inventory, teams struggle to answer basic questions: who published this integration, what data can it access, which version is approved and how can it be disabled?

A registry provides a discovery and governance layer. It does not replace authentication or authorization at the tool itself, but it gives platform and security teams a place to manage the metadata and approval process around the agent ecosystem.

What changed in Google Cloud Agent Registry

Google Cloud's release notes dated 19 November 2026 say Agent Registry added MCP tool protocol-level metadata, including Identity-Aware Proxy policy hints for tool enablement and human-in-the-loop controls, along with provider metadata attributes in Preview. The same release notes list skill security scanning and governance as available from 6 November, with standalone skills generally available.

These capabilities are useful signals, but note the release status: the 19 November metadata additions are marked Preview. Check the current product documentation and supported regions before relying on them in a production design.

Registering a tool is only the first step

A useful registry entry should identify the publisher, purpose, version, supported inputs, data classification, owner, review date and permission model. Keep development and production tools separate. For skills, record the source package and the exact revision that passed review; do not allow an agent to download a mutable, unreviewed package at run time.

Security scanning can identify suspicious content, but a scan result is not a complete security assessment. Review the skill's instructions, dependencies, network access and expected side effects. Test the tool with a low-privilege identity before making it available to wider groups.

Keep enforcement at the point of use

A registry can describe a permission or approval rule. The tool service must still enforce it. Verify the caller identity, check access to the requested resource, validate arguments and record the action. For a consequential operation—such as changing a customer record or triggering a payment—require an explicit approval from an authorized person.

Keep a way to revoke a tool or publisher quickly. Monitor usage and investigate tools that begin requesting new permissions or unusual data. A registry is valuable when inventory, policy and runtime evidence remain connected.

A rollout that avoids tool sprawl

Start with a small group of approved MCP servers and skills. Assign an owner to each entry, set an approval route for new tools and review changes before publication. After rollout, compare registered tools with actual tool calls and remove entries that are no longer maintained.

The goal is not to create a catalogue that nobody checks. It is to make tool ownership, trust and permissions visible before agents can affect business systems.
