Secure CI/CD pipelines: a practical guide to reliable software releases

A deployment pipeline is part of the production security boundary. It can read source code, use credentials, publish artifacts and change live infrastructure. A reliable CI/CD design therefore needs more than a green build: it needs controlled permissions, repeatable artifacts, useful tests and a clear recovery path.

Make the pipeline reflect the release process

Start by mapping how code moves from a developer change to a production release. Identify who can approve a change, which checks must pass, how artifacts are produced and who can deploy them. Keep development, staging and production environments separate. The pipeline should express the same controls that the organisation expects people to follow manually.

Use protected branches or equivalent repository controls for important release branches. Require review for sensitive changes, especially workflow files, infrastructure definitions, dependency manifests and authentication configuration. Keep emergency procedures documented, but do not make routine deployment depend on a shared administrator credential.

Reduce workflow permissions

Give a workflow only the repository and environment permissions it needs. Many build jobs can run with read-only access. Separate the job that builds and tests code from the job that publishes or deploys an artifact. Protect production environments with approval rules where appropriate and scope the set of people or services that can approve a release.

Review every third-party action, reusable workflow and downloaded script. Pin actions to a verified commit SHA when using immutable references, and update those pins through a controlled process. Avoid piping arbitrary remote scripts directly into a shell. Treat a workflow dependency as production code because it may execute with access to repository or deployment privileges.

Handle secrets and cloud identity carefully

Never store long-lived cloud credentials in repository files or plain workflow variables. Prefer short-lived identity federation, such as OpenID Connect where the cloud provider supports it. Restrict the trust relationship to the exact repository, branch, workflow or environment that should assume the role. Review the permissions granted to that role and remove unused access.

Separate secrets by environment and rotate credentials when exposure is suspected. Do not print secrets in logs or place them in build artifacts. Remember that untrusted pull requests and forked contributions should not receive privileged secrets. A pipeline should be able to test untrusted code without allowing it to publish to production.

Build once and promote the same artifact

Reproducible builds reduce uncertainty. Pin dependency versions, use lockfiles and record the build inputs. Produce an immutable artifact with a version or digest, then promote that same artifact through testing and production environments. Rebuilding separately for each environment can create subtle differences between what was tested and what was deployed.

For higher-assurance workflows, add artifact attestations or provenance records so that downstream systems can verify where an artifact came from and how it was built. Scan dependencies and container images, but treat scanners as one control in a broader process. Define how the team evaluates a finding, determines exploitability and approves or blocks a release.

Choose tests that protect the business journey

Run fast unit and static checks early. Add integration tests for the services and databases the application depends on. Run browser or API end-to-end tests for critical journeys, such as sign-in, account permissions, order submission or a business approval. Include accessibility and performance checks where they are relevant to the product.

Keep test data deterministic and avoid relying on external systems that are unstable or expensive. When tests need a service dependency, use a controlled test environment or an appropriate test double. Flaky checks should be investigated because teams eventually stop trusting a pipeline that fails unpredictably.

Deploy gradually and observe the result

Use a deployment strategy that fits the application's risk and hosting environment. Rolling, canary or blue-green approaches can reduce the impact of a faulty release, but they require compatible data migrations and a way to compare old and new behaviour. Health checks should measure whether the application can serve real work, not merely whether a process is running.

Monitor error rates, latency, resource use and business outcomes after deployment. Define who receives an alert and what action is expected. If a release fails, the team should know how to stop a rollout, route traffic back or restore the last known-good version. Database changes often need a forward-compatible migration strategy because code rollback alone may not reverse a data change safely.

Make release quality measurable

Track deployment frequency, change lead time, change failure rate and time to restore service as operational signals. Use them to start improvement conversations, not to rank individuals. The goal is a release process that enables small, safe changes with quick feedback. A large manual checklist is not automatically safer if no one understands the checks or the evidence they require.
