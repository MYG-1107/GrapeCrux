Feature stores for real-time ML: freshness, consistency and serving

A model can be accurate in training and unreliable in production when the features available online differ from the historical data used to train it. Feature-store design is about making feature definitions reusable, timely and consistent across training and inference.

Separate feature definitions from model code

A feature is a measurable attribute derived from source data: recent transaction count, time since last activity or average basket value. A feature store provides a consistent way to define, document, materialize and retrieve those values for training and serving.

Without shared definitions, teams reimplement transformations in notebooks, batch jobs and online services. Differences in filters, time windows or null handling create training-serving skew. Keep feature logic versioned and review changes as data-product changes.

Understand offline and online paths

The offline store supports historical retrieval for training and evaluation. The online store serves current feature values with low latency for real-time predictions. A materialization process moves data between source pipelines and serving stores, while a registry describes feature definitions and ownership.

Make freshness visible. A prediction service should know whether a feature is current enough and what to do when an online value is missing. Not every feature needs millisecond freshness; set targets according to the business decision.

Prevent leakage and point-in-time errors

Training data must reflect what was knowable when a prediction would have been made. If a historical join includes information recorded later, evaluation becomes optimistic and production performance drops. Use event timestamps and point-in-time joins, and test late-arriving corrections.

Keep business event time distinct from ingestion time. Document how duplicates, out-of-order events and backfills affect online values. Version transformations so a model can be reproduced against the feature definitions it used.

Monitor serving and govern access

Monitor freshness, null rates, distribution changes, materialization lag, online read latency and missing keys. Define fallback behaviour but do not silently replace critical values with arbitrary defaults. Restrict sensitive features by user and workload identity, and avoid exposing personal identifiers through names or metadata.

  • Identify reusable features across teams or models.
  • Define event time, entity keys, ownership and freshness.
  • Implement point-in-time correct retrieval.
  • Validate offline-to-online parity.
  • Monitor drift, missing values and serving latency.
  • Set access, retention and lineage controls.

Example: avoid leakage in a fraud model

A fraud model may use the number of transactions in the previous hour. During training, the feature must include only events that were available at the prediction timestamp. If a later chargeback or corrected customer status is accidentally joined into the historical row, offline evaluation leaks future information and exaggerates model quality. Use point-in-time joins and test late-arriving events, corrections and duplicate messages.

In the online path, specify what happens when the feature is stale or missing. Some predictions can use a safe fallback; others should be flagged for additional review. The fallback must be explicit and measurable rather than an arbitrary default hidden in serving code.

Feature-level operational checks

  • Compare offline and online calculations for selected entities.
  • Monitor freshness, null rate, distribution and materialization delay.
  • Alert on unexpected feature changes after a source-schema update.
  • Track which model versions consume each feature group.
  • Restrict feature access based on workload purpose and sensitivity.

These controls help reproduce predictions and explain model behaviour when an incident or quality regression occurs.
