AI red teaming: a practical test plan for generative AI systems

A polished demo does not show how an AI system behaves under pressure. Red teaming exposes failure paths before real users or attackers find them. This guide explains how to plan realistic tests, capture evidence and turn findings into safer releases.

Red teaming is one part of holistic evaluation

NIST’s September 2026 ARIA Evaluation Planning Manual describes a holistic approach combining model testing, red teaming and user testing. Red teaming probes adversarial behaviour; model tests measure defined capabilities; user testing evaluates the complete product in real use.

A programme does not prove that a model is perfectly safe. It identifies important failure modes, tests safeguards, records residual risk and repeats the work after material changes.

Define scope, assets and attacker goals

Begin with intended use and meaningful harm. For an enterprise assistant, goals may include extracting confidential information, bypassing document permissions or causing an agent to take an unauthorized action. Map prompts, retrieval, memory, tools, APIs, identity, files and logs. Identify access rights and likely consequences of crossing each boundary.

Agree rules of engagement, test environment, data restrictions and escalation contacts before testing. Use synthetic accounts and clearly marked test data rather than experimenting against live customer records.

Build test families and measure results

Include direct and indirect prompt injection, multilingual attempts, malicious retrieved documents, sensitive-data requests, tool misuse, malformed arguments, excessive autonomy, denial-of-service patterns and attempts to reveal internal instructions. Include benign requests to measure false positives.

For each test, record expected safe behaviour, actual response, attack success, severity, affected boundary, reproducibility and evidence. Evaluate downstream system state as well as model text: an agent may refuse in its answer but still have made a tool call.

Remediate the cause and repeat

A failure may come from model behaviour, missing authorization, unsafe tool design, weak filtering or unclear product instructions. Fix the architectural cause where possible. Convert each finding into a regression test and rerun it after model updates, prompt changes, retrieval re-indexing or permission changes.

  • Choose one workflow and a bounded test scope.
  • Identify assets, trust boundaries and attacker goals.
  • Create benign, adversarial and boundary-crossing cases.
  • Run controlled tests and inspect real side effects.
  • Rank findings, remediate root causes and retest.

One red-team exercise is a snapshot, not a guarantee. Schedule repeat assessments for high-impact systems.
