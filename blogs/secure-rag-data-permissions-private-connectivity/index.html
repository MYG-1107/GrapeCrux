Secure RAG systems: data permissions, private connectivity and isolation

A retrieval-augmented generation system can expose information even when the language model itself is well protected. The difficult work is preserving source permissions across ingestion, indexing, retrieval, prompting and response delivery.

Relevance is not authorization

RAG combines a model with external documents or databases. It can ground answers, but it creates a route from a user query to information with different owners and access rules. If a vector index contains several teams’ documents, a broad retrieval identity can return records the requesting user should not see.

The core rule is simple: a semantically relevant document must still pass the user’s access policy before it reaches the model.

Carry source permissions into the index

During ingestion, capture stable document IDs, source ownership, tenant, classification, retention state and access-control attributes. Synchronize permission changes, document deletion and source revocation promptly. At query time, authenticate the user and apply access filters in a trusted application layer before context is passed to the model.

Where rules are complex, retrieve candidate records and re-check authorization against the source of truth. Do not ask the model to decide whether a person is allowed to see a document.

Separate networks and protect prompts

Google’s November 2026 RAG reference design separates subsystems using network boundaries and IAM permissions while using private addresses for data movement and internal communication. Apply the same principle on your platform: expose only necessary endpoints, keep data services on restricted paths and control traffic between ingestion, serving and front-end components.

Inspect documents for sensitive data before embedding. Encrypt data, restrict egress and screen prompts and responses for injection or disclosure. Keep trusted application instructions separate from untrusted retrieved text. Minimize prompt and completion logging.

Make retrieval auditable and resilient

Log user identity, query ID, document IDs returned, authorization decision, model version and tool actions without storing full sensitive content by default. Monitor stale index records, unusual access patterns, cross-tenant anomalies and retrieval failures. Decouple ingestion from serving, use retry queues and define freshness objectives.

  • Synchronize revocations and deletions into retrieval.
  • Enforce identity outside the model.
  • Segment ingestion, retrieval, serving and administration.
  • Test cross-tenant access, stale permissions and prompt injection.
  • Rehearse failure of authorization and indexing services.

Example: preserve permissions in a multi-team knowledge assistant

Imagine one vector index contains engineering, finance and human-resources documents. A user from engineering should not receive a finance policy simply because it is semantically close to the question. Store source identifiers and access attributes with each chunk, authenticate the requester and apply policy filters before context is sent to the model. For sensitive collections, re-check the source system before prompt construction, particularly when permissions can change during the day.

Deletion needs the same attention. If a document is removed or access is revoked, invalidate the associated chunks, cached retrieval results and derived summaries. Define a measurable propagation objective and alert when the index is stale beyond that period.

Security tests worth automating

  • Attempt cross-tenant and cross-department retrieval with test identities.
  • Revoke source access and confirm retrieval stops within the agreed window.
  • Insert prompt-injection text in documents and verify it cannot authorize actions.
  • Disable the policy service and confirm the system fails closed for protected data.
  • Inspect traces to ensure sensitive document content is not copied into broad-access logs.

Test retrieval, authorization, caching and response delivery together; checking the vector database alone is not enough.
