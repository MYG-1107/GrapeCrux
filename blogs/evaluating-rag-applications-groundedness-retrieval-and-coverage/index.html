How to evaluate RAG applications: retrieval quality, grounded answers and coverage

Learn how to test retrieval-augmented generation using representative questions, evidence coverage, citation checks, access controls and operational metrics.

By GrapeCrux Editorial Team

A retrieval-augmented generation application can produce a fluent answer while retrieving the wrong document, missing a key passage or exposing material the user should not see. Evaluation needs to cover the entire path from query interpretation to evidence retrieval and final response. This guide presents a practical testing approach for teams building internal knowledge assistants and customer-facing search experiences.

Build a representative evaluation set

Collect questions that reflect real user tasks, not only questions that are easy for the system to answer. Include common queries, ambiguous wording, misspellings, multi-part questions, no-answer cases and questions about outdated material. Use permissioned examples and remove personal or confidential information that is not required for testing. Record expected sources or facts so reviewers can evaluate consistently.

Measure retrieval separately

Check whether relevant documents appear in the retrieved set and whether important passages are ranked high enough to be used. Useful measures include precision, recall and ranking measures such as reciprocal rank, but metric choice depends on the application. Inspect failures manually: a high-level document may match the topic while the specific policy section is missing.

Assess grounding and citation quality

Compare generated claims with the evidence supplied to the model. Check whether every important factual statement is supported, citations point to the correct source and the answer communicates uncertainty when evidence is incomplete. A citation that links to a relevant-looking page is not enough if the linked passage does not support the claim.

Test permissions and unanswerable queries

Verify retrieval applies the same user and tenant permissions as the source system. Test direct requests for restricted records, indirect attempts through related documents and changes in user role. Also test questions for which no approved answer exists. A safe system should say that it cannot find sufficient evidence rather than fabricate a response.

Include freshness and content operations

Documents change, access rights change and indexes can become stale. Test ingestion delays, failed refreshes, deletions, duplicate documents and revised versions. Track when a source was last indexed. Define an owner and process for removing information that is obsolete or no longer authorised for retrieval.

Measure user and operational outcomes

Track answer usefulness, escalation, correction, latency, token use and cost per successful task. Review feedback alongside technical metrics; low satisfaction may reflect an incomplete knowledge base rather than a model problem. Re-run the evaluation set after changes to the model, embedding, chunking, prompt, reranker or access-control logic.

Key takeaway: Evaluate RAG as a complete evidence pipeline: retrieval, permission checks, grounded answers, freshness and user outcomes.
