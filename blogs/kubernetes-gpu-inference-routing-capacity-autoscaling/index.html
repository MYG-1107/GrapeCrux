Kubernetes GPU inference: routing, capacity and autoscaling patterns

Serving generative AI models on Kubernetes is a capacity and routing problem as much as a container deployment problem. Teams need to match each request to a suitable model server while protecting latency, GPU memory and cost.

Why a model endpoint is not enough

A production inference service may host several model families, versions, quantization profiles and hardware pools. A single endpoint simplifies clients, but a backend still needs to decide which server can handle each request while meeting security and performance requirements.

Google Cloud’s November 12, 2026 GKE inference reference architecture describes a gateway in front of inference pools, with a unified interface, intelligent routing and centralized authorization. Similar patterns can be applied with other Kubernetes and serving stacks.

Route using workload characteristics

Route based on model identity, capabilities, context length, batchability, tenant, priority and available capacity. Consider queue depth, active sequences, GPU memory pressure and cache locality rather than CPU utilization alone. A model server that looks lightly loaded may be saturated by long-context requests.

Keep routing policy explicit and test fallback when a model is unavailable or capacity is exhausted. Do not route sensitive workloads to a model with different data-handling properties without approval.

Schedule GPUs as scarce resources

GPU workloads compete for accelerator memory, compute and network bandwidth. Use supported device plugins and node placement controls to isolate compatible workloads. Account for model loading time, fragmentation, warm capacity and the cost of keeping replicas ready. Separate batch jobs from interactive traffic where possible.

Set quotas and priority classes so low-priority embedding jobs do not consume capacity needed by customer-facing inference.

Scale with queue and latency signals

Traditional CPU-based autoscaling may react poorly to GPU inference. Monitor queue length, time to first token, inter-token latency, active sequences, memory pressure and throughput per replica. Combine proactive capacity planning with policies that consider startup and model-loading delays.

Use admission control and bounded queues to prevent overload. Secure model artifacts and workload identities, deploy progressively and validate output quality as well as service availability when versions change.

Example: separate interactive and batch inference

A service may receive interactive chat requests alongside overnight document-embedding jobs. The two workloads have different latency objectives and capacity patterns. Put them in separate workload classes with resource quotas and scheduling priorities. Interactive requests can use warm model replicas and bounded queues, while batch jobs consume spare capacity or run in a scheduled window. If the gateway routes solely by model name, it may send both workloads to the same saturated pool.

Record the routing decision and model version so operators can explain why a request was sent to a particular pool. Keep tenant and data-handling requirements in the routing policy; a low-cost replica should not receive traffic it is not approved to process.

Capacity signals to monitor

  • Queue depth, queue wait time and request rejection rate.
  • Time to first token and inter-token latency for streaming responses.
  • GPU memory pressure, active sequences and throughput per replica.
  • Model load and node provisioning time during scale-out.
  • Cost per successful task and quality after model changes.

Test overload, cold start, node loss and rollback before increasing traffic. Autoscaling is not a substitute for admission control or a clear degraded mode.
