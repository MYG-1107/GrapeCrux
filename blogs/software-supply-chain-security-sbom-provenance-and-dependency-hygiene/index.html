Software supply-chain security: SBOMs, provenance and dependency hygiene

A developer-focused guide to dependency risk, software bills of materials, build provenance, release integrity and vulnerability response.

By GrapeCrux Editorial Team

Modern applications depend on open-source packages, build tools, container images, CI runners and external services. A vulnerability or compromise in one dependency can affect many products. Software supply-chain security makes those dependencies visible and adds controls around how code is built, tested and released.

Know what your software contains

Maintain an inventory of direct and transitive dependencies, including versions and sources. A software bill of materials can help teams identify where a vulnerable component is used. SBOMs are most useful when generated consistently, linked to a release and updated as dependencies change.

Control dependency selection

Prefer maintained packages with clear release practices and appropriate licensing. Pin versions, use lockfiles and approved registries, and review new dependencies before adoption. Minimise package count where practical. A package name that appears familiar is not proof that it is the intended library or publisher.

Protect the build environment

Use isolated build runners, short-lived credentials and least-privilege workflow permissions. Protect release branches and require review of CI changes. Separate the authority to build software from the authority to publish or deploy it. A compromised build workflow can undermine otherwise sound application code.

Establish provenance and integrity

Record which source revision, dependencies, build process and artifacts produced a release. Sign artifacts where the environment supports it and verify signatures before deployment. Keep logs that allow the team to investigate whether an artifact came from an approved process.

Respond to vulnerabilities systematically

Assess whether a vulnerable component is present, reachable and exposed in the deployed context. Prioritise based on exploitability and impact, not only a numeric severity score. Plan upgrades, test compatibility, document exceptions and track remediation to completion.

Make the controls part of delivery

Add dependency scanning, secret detection, license review and build verification to CI. Define an exception process with an owner and expiry. For regulated products, align evidence and lifecycle controls with applicable quality and security obligations.

Key takeaway: Make dependencies visible, protect build authority and connect each released artifact to a traceable build process.
